# Utility file specifications (usage / content details)

### `tumplan/trajdata/initializer.py`

* Inputs: `config.simulator.data_input` (path / dataset name + selection e.g., scenelist)
* Work:

  * instantiate Trajdata loader: loads `SceneDataset` or `UnifiedDataset` (whatever Trajdata exposes).
  * run `compatibility_checks` to ensure required columns (`agent_id`, `state[:, x,y,heading,vx,vy]`, `timestep`) exist.
  * Optionally extend `SceneMetadata` with `planning_problem` field: `{ego_init_pose, goal_region, goal_time_window}` (structured).
* Returns: `dataset_loader` generator or list of `Scene` objects.
* Reason: centralize interactions so rest of code receives standard `Scene` objects.

### `tumplan/trajdata/scene_wrapper.py`

* Functions:

  * `get_ego(scene) -> AgentTrajectory` (explicit: if scene lacks a marked ego, use agent with `is_ego` flag or a config-provided agent_id).
  * `get_agents(scene, t) -> list[AgentState]`
  * `agent_bbox(agent_state) -> polygon`
* Keep minimal — no emulation of entire Trajdata API.

### `tumplan/utils/trajdata_eval.py`

* Functions:

  * `compute_collision(trajectory, agents, vehicle_model)`
  * `compute_metrics(traj, gt)`
  * `export_stats(log_path, dataset_meta, metrics)`

### `tumplan/utils/scene_metadata.py`

* Functions:

  * `attach_planning_problem(scene, ego_init, goal_region, goal_time_window)` — persists metadata in `scene.metadata` for TUMPlan to read.
* Reason: solves the "initial pose / goal region / time interval" problem without changing upstream dataset shape.

# Important design decisions & how to implement them (no-jugaad, native approach)

1. **Single bootstrapper**: Only one place (`initializer.py`) touches Trajdata dataset construction. Rest of code consumes `Scene` objects. This is *not* a wrapper layer — it’s a necessary instantiation point.

2. **No per-module wrappers**: Replace code that called `scenario.get_objects()` or `scenario.map` with direct calls to `scene` fields (via small helper functions in `scene_wrapper.py`). Search-and-replace the CR API usage and replace with standardized helper calls.

3. **Initial ego & goal**:

   * Best practice: store them in `scene.metadata.planning_problem` (added by `initializer`), not as a new agent in data. The planner reads `scene.metadata`.
   * If dataset tooling prevents metadata extension, fallback: provide a config file mapping `scene_id -> planning_problem`. But prefer metadata.

4. **Map & route**:

   * Trajdata datasets often lack full HD map. If map exists, use route planner that queries the provided map. If not, build a lightweight lane-graph approximator from agent trajectories (snap historical paths into a topological graph) — implement as `route_planner_trajdata` fallback.

5. **Collision checks / vehicle model**:

   * Keep `VehicleModel` usage. Compute agent geometry from Trajdata agent shape fields or bounding box params.

6. **Visualization**:

   * Move per-step heavy plotting out of loop. Collect ego + agents trajectories; run `trajdata_visualization.plot_scene(scene)` at the end. This reduces runtime overhead.

# Edge cases, risks & mitigations

1. **Maps missing or different formats**

   * Risk: route planner expects HD map.
   * Mitigation: implement fallback lane-graph builder from trajectories; keep route planner modular.

2. **Scenes without explicit ego agent**

   * Risk: Trajdata scenes may not mark ego.
   * Mitigation: allow `initializer` to assert an ego via config (scene id mapping), or attach ego in `scene.metadata`.

3. **Different time indexing**

   * Risk: Trajdata uses different timestep sampling.
   * Mitigation: convert to TUMPlan internal dt at initializer stage.

4. **Large refactor causing breakage in many callsites**

   * Mitigation: do incremental changes; keep a compatibility test harness that compares outputs of old CR run vs Trajdata run for a small set of scenarios.
